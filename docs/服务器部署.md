# SCAN-Planner deployment in this workspace

SCAN-Planner is a ROS local planner for route-guided quadruped navigation. It
accepts odometry, a LiDAR point cloud and a reference path or goal, then
publishes a collision-aware B-spline. It is separate from the NavDP learned
policy and does not require a checkpoint.

## Go2 quadruped locomotion in a cluttered warehouse

The active test now uses the floating-base Unitree Go2 MuJoCo model with 12
joint torque motors and physical foot/ground contact. Its base pose and
velocity are never prescribed after an episode reset. A pretrained
`rl_sar/go2/robot_lab` policy converts body velocity commands into joint targets;
PD control (kp=20, kd=0.5) applies bounded motor torques. MuJoCo dynamics run at
200 Hz, policy inference at 50 Hz, and the native SCAN trajectory controller at
100 Hz. This is articulated quadruped physics, not a planar robot proxy or a
kinematic body with animated legs.

### Scenario and navigation

The default is **one fixed scene and one algorithm run**, then automatic exit.
`go2_path_obstacles_scene.json` retains a reproducible 12.4 x 7.2 m warehouse:
15 background boxes/cylinders, three red blockers, and four boundary walls
(22 obstacles total). The three red objects are centered directly on the
start-to-goal reference at x=2.44, 5.24 and 7.70 m. The same scene is reused on
each launch; there is no default scene randomization or episode loop.

Global A* first constructs a reference from the **known background floorplan**,
with 0.65 m center clearance and line-of-sight simplification. The red
blockers are deliberately **excluded from the supplied
reference**: SCAN must detect them with live LiDAR and locally deviate from the
gray route. A second A* on the full actual geometry checks traversability before
launching the episode; its detour is saved for diagnostics, never fed to SCAN.
This is a partially known synthetic-map obstacle-avoidance test.

`go2_cluttered.launch` runs SCAN in native reference-path mode (`/initial_path`).
SCAN locally replans B-splines using live MuJoCo ray LiDAR: three vertical layers,
180 azimuths each, 360-degree coverage, and 5 m range. Ground and robot self-returns
are excluded. Collision checking uses double cylinders of radius 0.40 m and
offset 0.16 m. Hits are inflated 0.65 m downward so the elevated sensor's returns
reach the body-height planning slice, including at close range.

The existing `scan_closed_loop_controller` subscribes to `/planning/bspline`
and actual robot odometry, then publishes body velocity commands on
`/scan_sim/cmd_vel`. `mujoco_ros_bridge.py` forwards commands to the simulator
and publishes `/test/odom`, `/test/cloud` and the 12 articulated `/joint_states`.
The Go2 locomotion policy drives the twelve joint motors. Physical base motion
feeds back into the planner. Full base attitude and measured world velocity
are included in SCAN's odometry convention.

Each episode allows 180 seconds. Goal success requires distance below 0.30 m
and no fall; height below 0.14 m or roll/pitch above 1.0 rad marks a fall. The
simulator records the result, finalizes the video and exits after one test.
The supervisor then stops its bridge, planner and controller automatically.
The simulator owns each episode's scene and reference; the bridge receives the
reference with the tagged sensor packets. At each episode boundary the bridge
restarts its own ROS planner/controller process group before publishing reset
odometry. This clears old map occupancy, path progress and execution state;
commands remain gated until a fresh trajectory for the new reference arrives.
Obstacle collision substeps count actual robot/obstacle contacts, while normal
foot/floor contacts are recorded separately. `min_footprint_clearance` is a
conservative horizontal disk estimate (0.43 m radius), not an exact mesh distance.

### Detached GPU 4 execution and recording

To run selected candidate scenes once each, sequentially, with separate results:

```bash
python /home/hexiao/3d-navigation/runs/scanplanner/run_selected_gpu4.py 2 4 5 6
```

This uses the same detached `scanplanner-gpu4` tmux session and refuses a second
concurrent queue. `latest/status.json` tracks the queue; `scene_NN/` contains
each fixed input, planner/bridge/simulator logs, telemetry, result and video.
Every scene gets fresh planner/controller processes and a fresh observation map.
Each test ends on goal, fall or 180-second timeout; all selected tests run once
and the queue then exits. `results.json` retains outcomes and full video decode
checks. The usual `stop_gpu4.sh` stops the active scene and remaining queue.

For a single fixed default scene:

```bash
bash /home/hexiao/3d-navigation/runs/scanplanner/start_gpu4.sh
```

The dedicated tmux server/socket `scanplanner` and session `scanplanner-gpu4`
remain running when the terminal closes. The launcher refuses duplicate
sessions. It supervises the planner/controller, bridge and simulator together,
with the bridge managing a fresh planner/controller per episode, and stops the
remaining components if one exits. It reuses the existing ROS
master; otherwise roslaunch starts one. A shared ROS master is left running
when stopping this test.

GPU selection uses `CUDA_DEVICE_ORDER=PCI_BUS_ID`, `CUDA_VISIBLE_DEVICES=4`, and
`MUJOCO_EGL_DEVICE_ID=5`. On this machine EGL index 5 maps through DRM card6 to
PCI 81:00.0, physical GPU 4 (RTX PRO 6000). EGL indices are not nvidia-smi indices;
recheck the mapping if hardware changes. Rendering uses GPU 4; MuJoCo dynamics,
SCAN, the small ONNX locomotion actor and H.264 encoding run on CPU.

Outputs are under `runs/scanplanner/<Hong-Kong-time>_gpu4/`, with a `latest`
symlink. Videos in `videos/episode_NNNN_part_NNN.mp4` are 960x640, 20 fps, H.264.
The full-scene view shows cyan local plans, a yellow executed track and a green
goal. A camera inset shows actual joint-driven foot motion. Each video's title
includes the episode number and seed. Red objects block the gray
reference; cyan is the live local plan and yellow is the physical executed track.
Each episode or 60-second part is finalized separately; active files use fragmented MP4 so
completed fragments remain readable during recording. The encoder has its own
session, and graceful shutdown finalizes the active file.

`status.json` is updated each second. `telemetry.csv` contains base pose,
roll/pitch/yaw, velocities, commands, foot contacts and all twelve joint angles.
`episodes.jsonl` records completed results, layout hashes, seeds, contact counts
and maximum deviation from the reference. Each
`episodes/episode_NNNN/configuration.json` retains the actual scene, reference,
and diagnostic feasibility route; `executed_track.json` retains the completed
physical track. `scene.json` and `global_route.json` snapshot the current episode.
Logs are in `planner.log`, `bridge.log`,
`simulator.log` and `supervisor.log`.

The fixed fixture retains its generation seed for traceability. An optional
`--randomize --seed N --episodes K` simulator mode remains available for explicit
experiments, but the launcher runs only the fixed scene once. Physics/contact
success must be checked in `episodes.jsonl`.

```bash
cat /home/hexiao/3d-navigation/runs/scanplanner/latest/status.json
tail -f /home/hexiao/3d-navigation/runs/scanplanner/latest/simulator.log
tmux -L scanplanner attach -t scanplanner-gpu4
# Detach with Ctrl-B then D. Stop gracefully:
bash /home/hexiao/3d-navigation/runs/scanplanner/stop_gpu4.sh
```

### Assets, policy and dependencies

- Robot: `third_party/unitree_mujoco/unitree_robots/go2/`, from
  https://github.com/unitreerobotics/unitree_mujoco, pinned in `SOURCE.json`.
- Policy and deployment configuration: `third_party/rl_sar_go2/policy/go2/`,
  from https://github.com/fan-ziqi/rl_sar, pinned in `SOURCE.json`.
- Source licenses are retained in each vendored directory.
- `policy.onnx` was exported from the supplied TorchScript actor, including its
  observation normalizer. Ten parity samples compare against TorchScript with
  maximum absolute output error below 1e-5, in `export_validation.npz`.
- Runtime dependencies in `scanplanner-mujoco`: MuJoCo 3.4.0, NumPy 2.2.6,
  SciPy, ONNX Runtime 1.23.2; system ffmpeg with libx264/drawtext is used.
- `--primitive-visuals` is a diagnostic rendering option; it removes mesh skins
  while retaining exactly the same inertias, collision geometry and motors.
  The normal launcher uses the full 16-mesh Go2 model.

## Gazebo status

Gazebo Classic 11 was installed and launches with the system Ubuntu build, but
the provided container has no desktop graphics runtime. Gazebo exits with an
OGRE/OpenGL plugin or Xvfb cleanup failure in this headless session, before a
stable rendered LiDAR simulation can run. The Conda Gazebo build also fails to
load its OGRE renderer plugin.
The verified simulator integration is the MuJoCo ray-sensor run above, not
a Gazebo physics run. A Gazebo integration still needs a working display or a
container image with a validated headless OGRE/GL setup, then a compatible
quadruped Gazebo model and sensor plugin.

The upstream SCAN package supports its own ROS simulator (MockaMap plus local
sensing) and Gazebo is not required by the planner algorithm. The official
SCAN-Planner source/docs are at
https://github.com/wuyi2121/SCAN-Planner; this workspace's bundled integration
was sourced from https://github.com/atom-1024/legbot-3d-navi.
